1 · Executive summary

51%
Sub-standard weighted

The platform has a genuinely good architecture and, in several areas, a level of AEGIS fidelity well above what a prototype normally reaches. The homestay monitoring suite — a 24-item health & safety checklist, a 38-item annual visit report, an in-person-visit gate that blocks placement — is a faithful, working implementation of Standard 5.10 and most of 5.5. Private fostering (Standard 8) correctly models the six-week LA notification window, structured stakeholder briefings and multi-party consent. Student held funds, the mental health suite, welfare cadence and the training engine are all real, persisted and alerting.

Against that, roughly half the standards are not met — and the failures fall into three recognisable patterns rather than being scattered.

Accreditation readiness: not ready. AEGIS awards accreditation only where requirements are fully met.

1.2 The three failure patterns

Pattern A — The governance layer was never built

AEGIS is at its core a documents-and-policies inspection; Appendix A lists 30 essential documents for submission. The platform has an excellent policy store — og_org_documents, with versioning, review dates and a full audit history in policy-viewer.html — but only two documents are seeded into it, and nothing anywhere states which policies AEGIS actually requires.

There is no handbook store 2.3 no insurance record 2.4 no ICO registration or data controller 2.7.2 no code of conduct 2.1.6 · 5.8.2 no job descriptions 2.1.3 no complaints register Std 7 no statement of aims 1.1 and no significant-changes log 2.11. Each is a required AEGIS artefact; each is simply absent from the data model. This single pattern accounts for the majority of lost score.

Pattern B — Critical pages are static mockups

63 of 179 pages make no data call at all. Most are innocuous confirmation screens. Four are not:

  • admin-dashboard.html — the landing page and primary operational surface — contains no <script> tag whatsoever. Every figure is hardcoded: “28 students under active guardianship” (the database holds 6), “11 approved homestays” (it holds 2), “2 DBS records need action”. None derives from generateComplianceAlerts(), which sits one call away and returns real alerts.
  • compliance.html — the “AEGIS Control Room”, the page an inspector is shown first — is likewise fully static. Its DBS tracker names Margaret Ellis and Catherine Brennan, neither of whom exists in og_hosts.
  • audit-log.html — the audit trail evidencing Standard 2.5.1 — is static. No audit store exists in db.js.
  • low-level-concern-create.html — the creation path for Standard 6.5.2 — renders a full form whose “Save low-level concern” control is an <a href>, not a submit. It writes nothing. Same for concern-case, concern-close and concern-escalation, so the entire allegation triage workflow is a dead end — even though saveConcern() exists and is called successfully from three other pages.

Pattern C — Rich capture, no enforcement or alerting

The annual visit report captures, as structured yes/no/na items, “No more than three students will be hosted”, “If a student under 16 is placed, no student over 20 will be hosted”, “No other paying guests or bed and breakfast arrangements”. These are hard AEGIS placement rules 5.5.25.5.55.5.6. They are recorded as a point-in-time observation and read back on host-profile.html — but nothing consumes them as a rule. homestay-create.html will happily create a fourth placement.

Likewise og_org_documents tracks policy review dates and policy-viewer.html renders an overdue badge — but generateComplianceAlerts() never reads the policy store, so an overdue statutory policy review, exactly what Standard 2.10.1 exists to prevent, produces no alert anywhere.

2.2 Data flow — one database, many views

Every page in old_version/ loads <script src="assets/db.js"></script>, resolving to old_version/assets/db.js. That file declares 35 localStorage keys, seeds them idempotently via a series of init*DB() calls, exposes ~140 functions both as bare globals and as window.OG_DB.* (pages use both styles interchangeably), and runs migrateComplianceData() at load to backfill missing compliance objects. This is the right pattern and it is followed consistently — almost every fix in this report is a change inside db.js plus a small render change on one or two pages.

Recommendation

old_version/assets/db.js is unambiguously canonical — every live page resolves to it and it is 343 lines ahead. Delete assets/db.js from the repository root, along with root policy-viewer.html, which is a byte-identical duplicate. The root should retain only index.html and assets/app.css.

If the intent is eventually to promote old_version/ to the root, do it as a single explicit git mv rather than maintaining a mirror; the current arrangement guarantees any fix applied to one copy is eventually lost when someone edits the other. The directory name old_version/ is itself a hazard — it names the live application as though it were archived, which is how a mirror came to be treated as the real thing. Rename it to app/ in the same change.
